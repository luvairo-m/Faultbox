# Faultbox

Faultbox — учебная CLI-утилита на Python для имитации сбоев внешних HTTP API. Она запускает локальный HTTP-сервис и выдаёт ответы по TOML-сценарию: с заданными статусами, телами, заголовками, задержками и последовательностями.

**Статус: в разработке.** Ниже описано целевое поведение проекта. Python-пакет и команды CLI пока не реализованы; установка и запуск ещё недоступны. Требуемая версия Python — 3.11+.

## Для чего нужен Faultbox

При тестировании бэкенда адрес внешней зависимости заменяется адресом локального Faultbox. Сценарий задаёт воспроизводимое поведение API, чтобы проверить:

- повторные попытки после временных ошибок;
- обработку неуспешных HTTP-статусов;
- поведение при медленном ответе зависимости;
- восстановление работы после серии сбоев;
- обработку заданного тела ответа и заголовков.

Например, последовательность **500 → 500 → 200** означает, что первые два запроса получают ошибку сервера, а третий и все последующие — успешный ответ. Такой сценарий помогает проверить, что бэкенд повторяет запросы и корректно обрабатывает восстановление зависимости.

## Возможности

- Один TOML-файл описывает маршруты и шаги ответов.
- Маршрут определяется HTTP-методом GET или POST и путём запроса.
- Каждый шаг задаёт статус, тело, заголовки, задержку и число выдач ответа.
- Шаги выполняются последовательно; последний повторяется бессрочно.
- Маршруты имеют независимое состояние в памяти.
- CLI проверяет сценарий перед использованием и запускает локальный сервер.

## Сценарий TOML

Маршруты объявляются через `[[routes]]`, а их шаги — через `[[routes.steps]]`.

```toml
[[routes]]
method = "GET"
path = "/payments"

[[routes.steps]]
status = 500
body = "Temporary failure"
repeat = 2

[[routes.steps]]
status = 200
body = "Recovered"
delay_ms = 100
headers = { "Content-Type" = "text/plain; charset=utf-8" }
```

Здесь первые два запроса `GET /payments` получают статус 500. Начиная с третьего запроса сервер выдаёт статус 200 и тело `Recovered` с задержкой 100 мс. Последний шаг продолжает действовать до перезапуска сервера.

### Маршрут

| Поле | Описание |
| --- | --- |
| `method` | Метод запроса: `GET` или `POST`. |
| `path` | Путь запроса, например `/payments`. |
| `steps` | Последовательность шагов ответа, задаваемая таблицами `[[routes.steps]]`. |

Ключ маршрута — пара `(method, path)`. Поэтому `GET /payments` и `POST /payments` могут иметь разные сценарии. Query-параметры запроса игнорируются при выборе маршрута: `/payments?id=1` и `/payments?id=2` используют один маршрут. Пути `/payments` и `/payments/` различаются.

### Шаг ответа

| Поле | Тип | Значение по умолчанию | Описание |
| --- | --- | --- | --- |
| `status` | Целое число | Обязательное поле | Конечный HTTP-статус от 200 до 599. |
| `body` | Строка | `""` | Тело ответа, кодируемое в UTF-8. |
| `headers` | Таблица строковых значений | `{}` | Заголовки ответа: имя → значение. |
| `delay_ms` | Целое число | `0` | Задержка перед отправкой ответа в миллисекундах. |
| `repeat` | Целое число | `1` | Общее число выдач шага до перехода к следующему. |

`repeat = 2` означает две выдачи всего. Для последнего шага ограничение числа выдач не действует: он повторяется бессрочно.

### Состояние и одновременные запросы

У каждого маршрута свой счётчик шагов, общий для всех его клиентов. Запросы к одному маршруту совместно расходуют его последовательность; запросы к другим маршрутам не меняют этот счётчик. Перезапуск Faultbox сбрасывает состояние всех маршрутов.

Шаг назначается запросу атомарно и расходуется до ожидания `delay_ms`. Поэтому медленный ответ не задерживает назначение следующего шага другому запросу. При разных задержках ответы могут завершаться в другом порядке, чем назначались шаги.

### Проверка конфигурации

Ошибками сценария считаются:

- неизвестные поля и повторное объявление одной пары `(method, path)`;
- HTTP-статусы вне диапазона 200–599;
- непустое тело ответа для статусов 204, 205 и 304;
- попытка задать служебные заголовки `Content-Length`, `Transfer-Encoding` или `Connection`: ими управляет сервер.

## Интерфейс CLI

Предусмотрены команды:

| Команда | Назначение |
| --- | --- |
| `faultbox --help` | Справка по интерфейсу. |
| `faultbox check scenario.toml` | Проверка TOML-сценария. |
| `faultbox run scenario.toml` | Запуск локального HTTP-сервиса с выбранным сценарием. |

Это описание будущего интерфейса. Команды станут доступны после реализации пакета. Успешная проверка сценария должна завершаться с кодом 0; ошибка конфигурации или запуска — с ненулевым кодом.

## Границы проекта

Faultbox предназначен для локальных воспроизводимых сценариев тестирования бэкенда. В текущий объём проекта входят HTTP, фиксированные последовательности ответов и состояние в памяти. Прокси-режим, TLS, база данных, пользовательский веб-интерфейс и случайные сбои в этот объём не входят.
