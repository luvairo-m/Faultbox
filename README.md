# Faultbox

Faultbox – учебная CLI-утилита на Python для имитации внешних HTTP API. Она запускает локальный HTTP-сервис и выдаёт ответы по TOML-сценарию: с заданными статусами, телами, заголовками, задержками и последовательностями. Условия по заголовкам и query-параметрам позволяют выбирать разные сценарии для одного пути.

**Проект в разработке.** Пакет устанавливается на Python 3.11+, доступна справка `faultbox --help`. Остальные команды и возможности ниже описывают запланированный продукт. Имена полей и параметры CLI служат основой для реализации и могут уточняться вместе с контрактом.

План задач и отметки выполнения – в [PLAN.md](PLAN.md).

## Для чего нужен Faultbox

При тестировании бэкенда адрес внешней зависимости заменяется адресом локального Faultbox. Сценарий задаёт воспроизводимое поведение API, чтобы проверить повторные попытки, обработку ошибок и медленных ответов, восстановление зависимости и содержимое отправленных запросов.

Например, последовательность **500 → 500 → 200** означает, что первые два запроса получают ошибку сервера, а третий и все последующие – успешный ответ. После теста можно проверить число обращений и сбросить последовательность для следующего прогона. Несколько тестов могут использовать один сервер, сохраняя независимое состояние по заголовку `X-Test-Case-ID`.

## Возможности

- Маршруты GET/POST и последовательности ответов в одном TOML-файле.
- Статус, заголовки, тело UTF-8, задержка и число выдач каждого шага; последний шаг повторяется бессрочно.
- Тело ответа прямо в TOML или в отдельном файле через `body_file`.
- Выбор маршрута по методу, пути, заголовкам и query-параметрам запроса.
- Независимые последовательности и счётчики для разных маршрутов и тестов.
- Проверка сценария, запуск сервера и сброс состояния через CLI.
- Проверка точного количества обращений командой `verify`.
- Журнал запросов с подробным режимом для просмотра заголовков и тела.
- Готовые шаблоны сценариев через `init`, начиная с шаблона `retry`.
- Обработка отключений и тайм-аутов клиентов, управляемая остановка сервера при активных запросах.
- Понятные сообщения об ошибках чтения сценария, конфигурации и запуска.

## Пример сценария

Сохраните следующий пример как `scenario.toml`, а приведённый ниже JSON – как `responses/payment.json`. Это пример будущего формата, а не инструкция для уже доступного пакета.

```toml
[[routes]]
id = "payments"
method = "POST"
path = "/payments"

[[routes.steps]]
status = 500
body = "Temporary failure"
repeat = 2

[[routes.steps]]
status = 200
body_file = "responses/payment.json"
delay_ms = 100
headers = { "Content-Type" = "application/json; charset=utf-8" }

[[routes]]
id = "users-admin"
method = "GET"
path = "/users"
match = { headers = { "X-Client" = "backend" }, query = { role = "admin" } }

[[routes.steps]]
status = 200
body = '{"role":"admin","permissions":["read","write"]}'
headers = { "Content-Type" = "application/json" }

[[routes]]
id = "users-guest"
method = "GET"
path = "/users"
match = { query = { role = "guest" } }

[[routes.steps]]
status = 200
body = '{"role":"guest","permissions":["read"]}'
headers = { "Content-Type" = "application/json" }

[[routes]]
id = "users-fallback"
method = "GET"
path = "/users"

[[routes.steps]]
status = 400
body = "Unsupported role or missing X-Client header"
```

Файл `responses/payment.json`:

```json
{"payment_id":"payment-001","status":"accepted"}
```

Ожидаемое поведение:

| Запрос | Ответ |
| --- | --- |
| Первый и второй `POST /payments` в одной группе теста | 500, `Temporary failure`. |
| Третий и последующие `POST /payments` в той же группе | 200, содержимое `responses/payment.json`, задержка перед ответом 100 мс. |
| `GET /users?role=admin` с `X-Client: backend` | 200, JSON с правами `read` и `write`. |
| `GET /users?role=guest` | 200, JSON с правом `read`. |
| `GET /users?role=admin` без `X-Client: backend` | 400 от `users-fallback`. |
| `GET /users` без query-параметров | 400 от `users-fallback`. |

### Маршруты и условия

| Поле | Описание |
| --- | --- |
| `id` | Обязательный уникальный идентификатор маршрута для журнала и команды `verify`. |
| `method` | Метод запроса: `GET` или `POST`. |
| `path` | Точный путь без query-строки, например `/payments`. Пути `/payments` и `/payments/` различаются. |
| `match.headers` | Необязательная таблица условий по заголовкам запроса. |
| `match.query` | Необязательная таблица условий по query-параметрам запроса. |
| `steps` | Непустая последовательность таблиц `[[routes.steps]]`. |

Сначала сопоставляются метод и путь, затем проверяются все условия `match`: они объединяются через логическое «И». Значения сравниваются как точные строки, без регулярных выражений и шаблонов. Имена HTTP-заголовков сравниваются без учёта регистра, их значения – с учётом регистра. Имена query-параметров учитывают регистр; сравниваются декодированные значения. Для повторяющегося параметра достаточно одного значения, совпавшего с условием.

Из подходящих маршрутов выбирается первый в порядке TOML-файла. Поэтому общий маршрут без `match` размещается после условных вариантов для того же метода и пути, как `users-fallback` в примере. Если ни один маршрут не подходит, сервер возвращает 404 без расходования шагов сценария.

Заголовки и query-параметры, не указанные в условиях, на выбор маршрута не влияют. При отсутствии `match` учитываются только метод и путь. В отличие от исходного упрощённого варианта, одна пара `(method, path)` может иметь несколько вариантов с разными условиями и собственными `id`.

Тело запроса записывается в подробный журнал, но не участвует в условиях выбора ответа. Сопоставление по содержимому тела в описанный набор возможностей не входит. Заголовок `X-Test-Case-ID` зарезервирован для изоляции состояния тестов и не используется в `match.headers`.

### Шаг ответа и тело из файла

| Поле | Тип | Значение по умолчанию | Описание |
| --- | --- | --- | --- |
| `status` | Целое число | Обязательное поле | Конечный HTTP-статус от 200 до 599. |
| `body` | Строка | `""`, если не задан `body_file` | Тело ответа UTF-8. |
| `body_file` | Строка | Не задано | Путь к UTF-8-файлу с телом ответа вместо `body`. |
| `headers` | Таблица строковых значений | `{}` | Заголовки ответа: имя → значение. |
| `delay_ms` | Целое число ≥ 0 | `0` | Задержка перед отправкой ответа в миллисекундах. |
| `repeat` | Целое число ≥ 1 | `1` | Общее число выдач шага до перехода к следующему. |

`repeat = 2` означает две выдачи всего. Для последнего шага ограничение числа выдач не действует: он повторяется бессрочно.

Путь `body_file` разрешается относительно каталога TOML-файла, независимо от текущего рабочего каталога. `body` и `body_file` нельзя задавать одновременно. Файлы читаются при проверке и загрузке сценария; запущенный сервер использует загруженное содержимое. Изменение файла требует перезапуска сервера, а не `reset`. Ошибка чтения или некорректная кодировка отклоняет сценарий до запуска.

Тело может содержать обычный текст, JSON или намеренно некорректный JSON. Faultbox передаёт его как строку UTF-8 и не обязан разбирать как JSON. Тип содержимого задаётся заголовком `Content-Type` в сценарии.

### Независимые тесты и одновременные запросы

Состояние хранится в памяти отдельно для каждой пары `(route id, X-Test-Case-ID)`. Все клиенты с одним идентификатором теста совместно расходуют соответствующую последовательность. Разные идентификаторы начинают её независимо. Запросы без `X-Test-Case-ID` используют общую группу по умолчанию, отдельную от именованных тестов.

Например, первые запросы к `payments` с `X-Test-Case-ID: retry-a` и `X-Test-Case-ID: retry-b` оба получают 500. Третий запрос группы `retry-a` получает 200, даже если в группе `retry-b` пока был только один запрос.

Назначение шага и увеличение счётчика обращений выполняются атомарно до ожидания `delay_ms`. Медленный ответ не блокирует назначение шага другим запросам. Ответы могут завершаться в другом порядке, чем назначались шаги. Если клиент отключился после назначения, шаг и обращение остаются учтёнными.

Перезапуск сервера сбрасывает последовательности, счётчики и журнал в памяти.

### Сброс и проверка числа обращений

`reset` обращается к работающему Faultbox: он возвращает последовательности к первому шагу и обнуляет счётчики обращений. Без фильтра сбрасываются все группы тестов; `--test-case` ограничивает сброс указанной группой. Настройки и загруженные тела ответов сохраняются.

Уже назначенные запросы завершаются с прежними ответами; новые после сброса получают шаги с начала. Для воспроизводимого повторного теста следует дождаться завершения предыдущего прогона перед сбросом. Журнал сохраняет предыдущие записи и отметку сброса.

`verify --route payments --count 3` проверяет, что маршруту назначено ровно три запроса с последнего сброса или запуска. Без `--test-case` учитывается сумма по всем группам; с этим параметром – только выбранная группа. Это проверка числа обращений, а не числа успешно доставленных ответов. Команды управления не увеличивают счётчики сценариев, а `verify` не сбрасывает их.

### Журнал запросов

Обычный журнал в терминале показывает метод, путь, выбранный `route id`, группу теста и результат обработки запроса. Режим `run --verbose` дополнительно показывает заголовки, query-параметры и тело входящего запроса, чтобы сравнить фактическое обращение бэкенда с ожиданиями. Для тела, которое не является UTF-8, используется диагностическое представление без изменения полученных данных.

### Проверка конфигурации

Ошибками сценария считаются:

- неизвестные поля, повторные `id` и дубли вариантов с одинаковыми методом, путём и условиями;
- методы вне GET/POST, пустые списки шагов, неверные типы полей;
- HTTP-статусы вне диапазона 200–599, отрицательный `delay_ms` и `repeat` меньше 1;
- одновременное задание `body` и `body_file`, недоступные или не UTF-8 файлы;
- непустое тело ответа для статусов 204, 205 и 304, в том числе загруженное из файла;
- попытка задать заголовки ответа `Content-Length`, `Transfer-Encoding` или `Connection`: ими управляет сервер;
- использование зарезервированного `X-Test-Case-ID` в условиях маршрута.

## Проектируемый CLI

Сейчас работает `faultbox --help`. Команды `init`, `check`, `run`, `reset` и `verify` запланированы.

Для `run` по умолчанию используются адрес `127.0.0.1` и порт `8080`. `reset` и `verify` работают с уже запущенным сервером через отдельный локальный интерфейс управления. Они не изменяют состояние другого процесса напрямую и не запускают второй сервер. Адрес управления задаётся через `--server`; по умолчанию – `http://127.0.0.1:8080`. Служебные обращения отделяются от запросов сценария.

| Команда | Назначение |
| --- | --- |
| `faultbox --help` | Справка по интерфейсу. |
| `faultbox init retry` | Создать `scenario.toml` с маршрутом `payments` (POST `/payments`), последовательностью 500 → 500 → 200 и нужные файлы ответа в текущем каталоге. Существующие файлы не перезаписываются. |
| `faultbox check scenario.toml` | Проверить TOML, условия и файлы ответов. |
| `faultbox run scenario.toml --port 8080` | Запустить локальный сервер на `127.0.0.1:8080`. |
| `faultbox run scenario.toml --port 8080 --verbose` | Запустить сервер с подробным журналом запросов. |
| `faultbox reset --server http://127.0.0.1:8080` | Сбросить последовательности и счётчики всех тестов. |
| `faultbox reset --test-case retry-a` | Сбросить только группу `retry-a` на сервере по умолчанию. |
| `faultbox verify --route payments --count 3 --test-case retry-a` | Проверить ровно три обращения к `payments` в группе `retry-a` на сервере по умолчанию. |

Типичный будущий порядок работы:

1. Создать пример через `faultbox init retry` и при необходимости изменить сценарий.
2. Выполнить `faultbox check scenario.toml`.
3. В отдельном терминале запустить `faultbox run scenario.toml --verbose`.
4. Направить тестируемый бэкенд на `http://127.0.0.1:8080`, передавая `X-Test-Case-ID: retry-a` при обращениях к Faultbox.
5. Выполнить тест и проверить обращения через `faultbox verify --route payments --count 3 --test-case retry-a`.
6. Перед повторным прогоном выполнить `faultbox reset --test-case retry-a`.

Успешные команды и совпавший результат `verify` завершаются с кодом 0. Ошибки чтения, конфигурации, запуска, связи с сервером и несовпадение количества обращений дают ненулевой код с понятным сообщением. Остановка сервера выполняется через Ctrl+C.

## Локальная установка

Выполните эти команды в PowerShell из корня репозитория.

```powershell
python --version
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install .
.\.venv\Scripts\faultbox.exe --help
```

Для создания окружения нужен Python 3.11 или новее. Если `python` открывает Microsoft Store или не запускается, укажите полный путь к установленному интерпретатору в первых двух командах, например `& "C:\путь\к\python.exe" --version`.

Для работы над кодом установите пакет с набором `dev` вместо обычной установки.

```powershell
.\.venv\Scripts\python.exe -m pip install -e ".[dev]"
.\.venv\Scripts\python.exe -m mypy
.\.venv\Scripts\python.exe -m pytest
```

До появления тестов pytest завершает работу с кодом 5.

На Linux и macOS используйте `python3` для создания окружения, а затем `.venv/bin/python` и `.venv/bin/faultbox` для запуска инструментов.

## Границы проекта

В запланированный продукт входят локальный HTTP, TOML-сценарии, условия по заголовкам и query-параметрам, файлы ответов, состояние в памяти, изоляция тестов, сброс, проверка числа обращений, подробный журнал и готовые шаблоны. Прокси-режим, TLS, база данных, веб-интерфейс, случайные сбои и сложные шаблоны ответов остаются за пределами проекта.
